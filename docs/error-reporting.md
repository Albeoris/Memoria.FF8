# Reporting an error

Select **Report error** in the error window. Memoria prepares one local ZIP, reveals it in the file manager and opens a filled GitHub issue draft. Sign in to GitHub if needed, drag the ZIP into the issue body, wait for the upload and select **Submit new issue**. Reports and attachments are public. You may add what you remember doing directly in GitHub.

Opening the draft does not attach the file or submit an issue. If login loses the text, use **Open GitHub again** or **Copy full description**. **Show ZIP**, **Copy report path** and the selectable URL remain available when the browser or file manager cannot open. Memoria never copies anything to the clipboard without your action. Offline preparation still works; the browser needs a connection to GitHub later.

The error window immediately shows the incident date and time with the local UTC offset, subsystem, error summary and selectable local file path. **Copy incident path** works before preparing a report. After preparation, the incident path points to the ZIP. ZIP instructions and recovery actions appear only once a report is ready. **Delete incident** asks for confirmation, removes that incident's local recovery evidence and any prepared ZIP, then closes the window without opening GitHub. Ordinary saves, original logs and other incidents are kept. Closing the window alone keeps the incident.

Reports live in the user data directory resolved by `ApplicationPaths`, under `reports`. Each completed report directory contains only its ZIP. Recovery evidence is staged in the separate private sibling directory `reports.pending`; successful packaging removes the staged incident and save. A small presentation marker may remain there to avoid offering the same incident again. The latest ten completed reports are retained; reports being prepared or displayed are protected. Ordinary save banks are untouched. A retained incident can be offered by the launcher after the game renderer exits.

The ZIP includes `report.md`, the available exception tree in `exception.txt`, detached `runtime.json` and `environment.json`, a bounded semantic history in `events.jsonl`, `manifest.json`, recovery metadata, available reproduction saves and sanitized logs. Exported diagnostic text and JSON normalize local paths to neutral labels and redact recognized private fields and credentials. Review the ZIP before sharing: arbitrary free-form diagnostic text can contain information beyond the recognized patterns. Native termination may provide only process/bootstrap evidence. A managed stack is not invented for such failures.

A validated reproduction save is attached when available: compact snapshots use `repro/state.ff8save`, and JSON snapshots use `repro/state.json`. Account identity is excluded by the save writers and detached when loading historical saves; account delivery remains in the local achievement profile. Saves contain game state and resource identifiers rather than installed resource paths. Player-selected names and other in-game input are preserved. Timestamp and launch metadata are preserved as well.

Up to eight recent logs are attached under numeric names in `logs/`, with at most the latest 1 MiB from each original log before sanitization. An initial incomplete record is discarded when bounding a raw tail, and sanitized output is bounded as well. Text and JSON log records use the same path/account/credential sanitization as diagnostic text. Original log filenames and paths are not exported; the local source logs remain unchanged. Logs already attached to a recovered report are sanitized again and retained when launcher diagnostics enrich that report.

The package budget is 20 MiB. Logs and semantic history may be omitted to fit this limit. An available validated save is never silently dropped: if the save and required exception/context cannot fit, preparation fails with a size explanation while pending recovery evidence remains local. Successful packaging does not retain loose incident, save, description, completion or lease files beside the ZIP. The complete sanitized description remains in the ZIP and copy action even when the browser URL uses shorter text.

## Using the attached save

Read the capture kind, source timestamp, age and limitations in `report.md`. An earlier validated save is a recovery checkpoint and may precede the failure; its presence does not establish exact incident replay. A faulted boundary may have no safe validated save, which the report explains.

Extract the archive to a separate directory and launch the matching engine with `--state <extracted-save>` and matching edition, language, resources and mods. Use separate test save/settings directories and `--achievements-local-only` during investigation. See the [command-line reference](reference/command-line.md). Original snapshots remain readable; resaving creates the current account-independent representation without changing game names or input.

## GitHub handoff

The reporter uses only the fixed repository issue URL and the documented `title` and `body` query parameters. The complete percent-encoded URL is capped at 2,000 ASCII characters; full text stays in the ZIP and the copy action. No account token, reporting service, GitHub API submission, browser automation or automatic upload is involved.

GitHub documents [prefilled issue URLs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue#creating-an-issue-from-a-url-query) and [browser attachment support and limits](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files). ZIP files require a manual drop or file selection. The application can observe preparation and browser launch, but cannot observe upload or issue submission.

For manual acceptance, use synthetic diagnostics and an explicitly designated test repository. Check both signed-in prefill and signed-out login, reopen after login, one ZIP upload and final submission. Do not post test issues to the production repository. These authenticated checks require a tester's browser/account; portable automated tests cover local capture, archive contents, bounded Unicode URLs and failure handling.
