# Gameplay save component contracts

The opt-in component codec is separate from the existing execution snapshot and original FF8 save readers. It is an incremental building block for a gameplay save coordinator; it is not a complete playable save format and must not be routed into ordinary slots, quicksaves, transfers or update handoffs yet.

`GameplaySaveComponentDocument` version 1 declares its coverage as `characters,economy,limits`; its capture API takes those three owners explicitly. Version 2 adds `durable-progression` through `CaptureProgression(state, resume)`. It projects the root owners listed below, but does not certify a semantic scene reconstruction. No existing save reader, default writer, snapshot schema or extension dispatch changes to use this document. The same codec/signature carries both versions; version 1 remains readable and continues to represent component-only coverage.

## Ownership and absence

Current installed definitions are supplied to `Restore`. | Every component property is required. Missing or malformed data fails; known progress never falls back to a new-game value. The reused `NativeCharacterVital` and junction/stock scalar records currently contain only saved progression. A type-graph/property-ownership regression test makes adding installed resources or runtime state to these reused records an explicit review decision. Capturing and restoring detach mutable saved arrays; installed immutable definition objects remain the selected host's authority.

## Storage

`GameplaySaveCodec.Write` and `Read` operate on caller-owned streams and leave them open. The signature is `MFF8GPC1`, distinct from execution snapshot `MFF8SAVE`. The version 1 container is an eight-byte signature, four-byte container version, four-byte payload length, 32-byte SHA-256 checksum and UTF-8 JSON payload. Lengths are bounded to 4 MiB while writing and before allocating the read payload. Truncation, trailing bytes, checksum mismatch, unknown JSON members and unsupported format/version/coverage fail explicitly.

These component bytes contain no original save block, installed stat tables, source asset blobs, VM stacks, staging arenas or render objects. The codec does not claim atomic slot publication or a reconstructed gameplay load; those remain the future coordinator's responsibility. It must validate the full reconstructed candidate before publishing a player slot.

## GF progression and selected profiles

Character capture imports GF learning into the existing semantic ledger by ability identity. It first uses the runtime compatibility normalizer to adopt observed learned/AP/forgotten changes recorded against `LastProjection`; that projection is consumed, not written into the component. A projection without a ledger can use the observed native record when its learning map still agrees. An orphaned conflicting map remains an explicit recovery boundary.

Restore uses the supplied current profile and menu definitions, rebuilds native compatibility fields and a fresh `LastProjection`, then derives maximum HP. Changed source/kernel fingerprints alone do not prevent restore. Learned/AP/forgotten/item-taught history for removed abilities remains dormant and becomes usable again if the selected profile supplies those abilities. Learning selection follows the existing available-ability policy. The disabled Move-Find preference is preserved, as are exact saved HP and unrelated character/magic data; template application must not incidentally clamp HP, normalize inventory or discard junction choices during component reconstruction.

The optional `AbilityBindings` field stores twenty-one ability IDs alongside saved native AP/forgotten slots. It contains no AP requirements, learning conditions, templates or resource references. Rebinding moves the values by ability identity and occurrence, preserving distinct duplicate slots. Forgotten bits on unused rows and reserved high bits remain represented. Current-profile conditions remain authoritative. Older components without these IDs keep their legacy current-map interpretation; they cannot establish a lost historical mapping after an unrelated kernel changed it. New captures carry the mapping explicitly.

An observed opaque baseline with no reconciled current profile remains unsupported for component capture. Once a current profile has been reconciled, its current ledger is authoritative and unique known recovery abilities can be retained dormant; old compiled recovery resources and attribution history are excluded. Historical item-taught provenance not represented as item-taught in the current ledger remains an explicit capture refusal: the existing runtime activates item-taught entries, so clearing that fact or pretending it can remain inactive would change its meaning. This is not a promise to preserve a historical profile-undo workflow.

The optional `GuardianForceIntent` character member preserves save-local authoring documents, excluded contributions and local ownership aliases. Its version-1 DTO whitelists document/operation IDs, GF/ability IDs, replacement and initial-state choices, expected state/order and stable producer references. It supports the existing Ensure Ability, Replace Ability, Set Initial State and Order Subset contracts. Earned AP, learning selection, passive preference and form enable remain in their existing progression/preference owners; AP requirements come from the selected ability-point table rather than a saved installed template.

Capture verifies that the intent is already reconciled with current definitions; it does not turn a pending edit into committed progression. Restore composes the selected installed source/layers, saved exclusions and ordered local operations using the existing composer, then projects known progress by identity. Saved local ownership takes precedence if an installed document later appears with the same ID, excluding that installed contribution. A changed-mod operation conflict or missing producer remains an explicit reconciliation boundary instead of a silently skipped choice. These failures leave both input component and selected definitions unchanged.

Replacing a resource-native ability retains its complete source-slot group. The effective learning view changes the referenced ability ID while preserving slot order, requirement and exclusion bytes; dependencies still refer to the same table indices. Learning, forgetting, AP ownership, compatibility projections and semantic slot bindings use that view. Replacement into an already present ability remains an explicit operation conflict, and partial or overlapping native bindings fail validation. Removed earned progress remains dormant by ability identity; a replacement uses its configured initial state rather than inheriting the removed ability's earned AP. Duplicate slots retain their distinct AP bytes and suppression flags, with AP awards still owned by the first matching slot. Neither installed source tables nor old snapshot schemas are rewritten.

Native fingerprints, arbitrary document/operation extension data, compiled templates and source resource references are not stored. Producer/document keys are portable opaque identities: separators and suffixes such as `local/abilities.json` are allowed and do not cause filesystem access. Actual rooted/drive/file-URI references refuse capture rather than creating environment dependencies. Fresh runtime authoring documents contain only the whitelisted fields, with no extension metadata or old source fingerprint. Older components missing `GuardianForceIntent` preserve the previous selected-definition behavior.

The per-save GF-form enable choice belongs to gameplay preferences in the broader progression coverage. An active form's invocation, timer and presentation remain battle execution state and are not part of this nonbattle character component. Existing execution snapshots and original-save readers/writers are unchanged.

## Remaining coordinator work

Version 2's `Progression` has explicit required owner groups; each nullable member preserves unknown/absent state rather than initializing it from zero. Missing a required version 2 group fails. `GameplaySaveRootOwnership` classifies every `GameState` property, and its regression test requires a review when a root member is added.

| Group | Saved progression | Exclusions or separate reconstruction |
| --- | --- | --- |
| Story | Exact event cells with original widths, including represented field-local values; world-entry bytes, controls, disc, saved battle flags/knownness, saved fade and message-variable values. | Uncertain executed event reads require a semantic adapter. Physical fades and their active callbacks are not copied. Canonical root values are used rather than frozen VM mirrors. |
| Saved world | Both vehicle slots, Garden/Ragnarok parking, committed transport-return values, fuel, world-event flags/channels, terrain knownness, original angle words and bounded unresolved saved entry values. Field party poses and the world entity configuration are separate logical values. | Loader receipts, native provenance rules, source frame, scripted camera trajectory and allocation identities are excluded. A resume handler must reconcile the current world pose with saved parked vehicles, establish a normal-load source and reject unsupported transport state. |
| Collections | Appearance, cards/statistics/RNG, shop bytes, recipe/discovery bits, shot flags, PocketStation values/name, Chocobo reward/import ledger, known magic, Scan history and refined-card IDs. | Kernel ammo tables, initialization fingerprints and asset data are supplied by installed definitions. Active card matches remain unsupported. |
| Rules and choices | Current/configured/pending preferences, magic-mode review, already-earned pending name requests and drafts, input settings, encounter policy/progress, playthrough policy and dialogue choice draft. | A pending choice is preserved as data; no claim is made that its suspended modal VM can yet be reconstructed. Pending encounters are rejected. |
| Clocks | Quest timer alternatives and their correlation, elapsed playtime/fraction, RNG state, draw depletion/regeneration, salary/rank/movement progress. | Installed salary tables are excluded. Small timer callback counts/display correlation currently remain because transaction/timer invariants use them; they are not a native allocation graph. |
| Transactions | Battle totals/persistent AI variables, applied result IDs, achievement outboxes/owner bindings, draw/mutation/dedup cursors and committed abandonment facts. | Former abandoned VM waits and next-operation pointers are excluded. The new coordinator must restore acknowledgement/transaction ownership before issuing new facts; it must not replay committed rewards. |
| Scene facts | Names, tutorials, raw field-party order, party/menu/run/map flags, place, previous salary movement and scoped logical music choices. | Extraction uses the active field snapshot or current world event context. World-only snapshots may take unchanged names/tutorials/party from the authentic suspended field; its music facts remain separately marked `SuspendedFieldMusic` and cannot claim current-world authority. No complete VM JSON is stored and frozen mirrors never replace current shared root globals. |
| Original compatibility residue | The bounded 8,192-byte original save image and its original names, when present, preserve fields that lack typed owners. | This image is historical compatibility residue, not the current game's authoritative whole-save projection. Current typed components and current scene names take precedence during reconstruction. It must not be treated as a current original save and reimported wholesale. |

The ordinary gameplay normal-load policy deliberately starts a fresh process and rebuilds native working storage. That includes stale physical battle headers, last-action/healing ranges and released staging residue, which can affect exact native process continuation. Accumulated battle totals, progression, pending facts and reward receipts are preserved separately. This is a declared normal-load semantic boundary, not a claim that the old physical rows never matter. Legacy exact-snapshot readers must continue to preserve those rows and their original continuation.

Before enabling a complete gameplay writer, implement semantic scene bootstrap, settle/validate live transport and pending operation boundaries, supply a required gameplay-content compatibility policy and restore typed owners into current installed definitions. Local event values alone do not reconstruct actors, scheduler state or event stage. Resolved selected GF profiles and whitelisted local choices use the adapters above; ambiguous recovery and changed-operation conflicts still need explicit treatment rather than table embedding or silent loss. Existing snapshots retain their current continuation and reading behavior throughout this work.

`GameplaySaveWorldData.RestoreParkingAndFlags` is a resource-free restoration primitive for parked vehicles and saved flags; it deliberately clears old return receipts instead of promoting a historical return to the current world pose. The current `Resume.World` position drives a new supported normal-load return/entry contract, while parked vehicles and occupancy remain consistent. Normal saved-world entry uses entry 62 rather than replaying a prior field-exit `WorldArrival`. Normal saved-field entry uses load reason 0, sharing the saved-load process initialization contract rather than field-request reason 1. The bootstrap still needs to establish the appropriate initialized owner/provenance before calling the primitive.

A central host boundary evaluator and a registered semantic resume handler are both required. Player control by itself does not prove that a field VM can be discarded. No component method executes field initialization, replays script rewards or resets a running session. The later normal-load path must prove it preserves committed effects and all remaining gameplay owners before this component document can participate in a complete save.
