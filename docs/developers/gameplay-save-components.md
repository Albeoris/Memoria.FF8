# Gameplay save component contracts

The gameplay component codec is separate from the existing execution snapshot and original FF8 save readers. Ordinary Memoria slots, quicksaves and update handoffs use semantic gameplay documents at supported field/world exploration boundaries. Legacy snapshots and original saves remain readable; exact snapshots remain available to diagnostic tools.

`GameplaySaveComponentDocument` version 1 declares its coverage as `characters,economy,limits`; its capture API takes those three owners explicitly. Version 2 adds `durable-progression` through `CaptureProgression(state, resume)`. Projection alone does not certify a semantic scene reconstruction. Player loading detects the container marker, and slot metadata reads bounded components without opening installed resources. Legacy execution snapshots and original saves keep their existing readers. The same codec/signature carries both component versions; version 1 remains readable as partial coverage and is not presented as a loadable player save.

`GameWorld.CaptureGameplaySave` admits supported playable field exploration through typed logical scene/actor/script continuation, without replaying initialization. The continuation owns the full leader pose and field locals; historical menu-location caches and duplicate global/local cells are excluded. Ordinary world exploration captures one supported controlled transport and current host position/facts, rather than a historical return pose. A fresh original-PC field import can capture its allocated, not-yet-executed normal-load intent and saved party positions. Active battle, modal interaction and unsupported transient owners reject capture before publication. `WriteGameplaySave` stages the document in a unique file beside the destination, flushes it, loads it with the same selected assets and policy, and runs the caller's continuation validator before replacing the destination. A failure preserves the previous save and removes only that operation's staging file.

The player store can use this host writer for both manual slots and rotating quicksaves. It supplies monotonic quicksave file timestamps to the publisher and retires older files only after successful publication. The optional document `SavedLocalAt` records display metadata independently of filesystem copy times; older documents without it remain readable.

Copying between Memoria slots validates a staged byte-for-byte copy and retains the source format and metadata. It does not expand a semantic source back into an execution snapshot. Original-bank import can use a selected isolated gameplay publisher; its source and previous destination remain unchanged if validation fails.

Update handoff uses the same publisher. Its outer staging boundary still checks expiry and publishes without replacement; a destination created during validation is preserved, staging is retired, and the running host is not paused on failure.

Startup passes the completed launch configuration to the player loader before reconstruction, including selected mods, resource language and model source. Installed GF layers compose over fresh definitions before saved local intent, AP and learning targets are overlaid. Complete legacy snapshots keep lazy initialization and do not require opening an installation merely to deserialize their represented state. These are load-time definition choices, not saved compiled profiles or renderer caches.

Publication validation uses the current selected resource host's GF layers too. An older live snapshot's retained applied layer cannot substitute for the installed definitions that the next player load will select. The running session remains unchanged while the isolated candidate is rebuilt and checked.

Current installed definitions are supplied to `Restore`. | The original character owner properties are required. `GuardianForceIntent` and `PendingGuardianForceRecovery` are optional as described below. The reused `NativeCharacterVital` and junction/stock scalar records currently contain only saved progression. A type-graph/property-ownership regression test makes adding installed resources or runtime state to these reused records an explicit review decision. Capturing and restoring detach mutable saved arrays; installed immutable definition objects remain the selected host's authority.

Container, document and logical owner versions are independent. The current reader accepts document versions 1 and 2 with their declared coverage; it does not promote a version 1 partial document into a complete player save. Required nullable properties must still be present: explicit null records unknown state, and zero, false and empty arrays retain their represented meanings. Defaults never infer a missing feature from one of those values.

Later optional members retain their older interpretation when absent: `SavedLocalAt` supplies no timestamp, GF intent supplies no local operations, missing GF slot IDs retain the legacy current-map interpretation, and `FieldContinuation` supplies no retained field execution. Within a continuation, absent menu/ambient/particle owners supply no such retained operation; a corresponding wait still requires its complete owner. Missing `UseResourceLastPose` is false and preserves the explicit animation range. Optional script preparation/input metadata retains the earlier unprepared/idle baseline. Introducing an independently absent feature requires a documented baseline or migration; it must not make an older accepted writer's output require fabricated progress. Unknown members and unsupported future versions still fail explicitly.

## Storage

`GameplaySaveCodec.Write` and `Read` operate on caller-owned streams and leave them open. The signature is `MFF8GPC1`, distinct from execution snapshot `MFF8SAVE`. The version 1 container is an eight-byte signature, four-byte container version, four-byte payload length, 32-byte SHA-256 checksum and UTF-8 JSON payload. Lengths are bounded to 4 MiB while writing and before allocating the read payload. Truncation, trailing bytes, checksum mismatch, unknown JSON members and unsupported format/version/coverage fail explicitly.

Version 1's three component owners contain no original save block or VM stacks. Version 2 can retain bounded original compatibility residue and a typed logical field continuation, including script stacks, as described below. Neither version stores installed stat tables, source asset blobs, staging arenas or render objects. The stream codec itself does not publish slots or reconstruct gameplay; the host coordinator validates the full reconstructed candidate before publishing a player slot.

## GF progression and selected profiles

Character capture imports current native GF progress by ability identity. Existing semantic ledgers use the runtime compatibility normalizer to adopt observed learned/AP/forgotten changes against `LastProjection`. If the ledger is absent and that retained projection supplies complete unique old ability bindings, pure conversion imports the current native values through those IDs, then rebinds them through selected current definitions. Cached projection values are not restored as progress, and live definitions are not replaced. The old rule table is consumed, not saved. A missing projection retains the earlier current-map interpretation; malformed, unsupported or duplicate conflicting bindings remain explicit recovery boundaries.

Restore uses the supplied current profile and menu definitions, rebuilds native compatibility fields and a fresh `LastProjection`, then derives maximum HP. Changed source/kernel fingerprints alone do not prevent restore. Learned/AP/forgotten/item-taught history for removed abilities remains dormant and becomes usable again if the selected profile supplies those abilities. Learning selection follows the existing available-ability policy. The disabled Move-Find preference is preserved, as are exact saved HP and unrelated character/magic data; template application must not incidentally clamp HP, normalize inventory or discard junction choices during component reconstruction.

The optional `AbilityBindings` field stores twenty-one ability IDs alongside saved native AP/forgotten slots. It contains no AP requirements, learning conditions, templates or resource references. Rebinding moves the values by ability identity and occurrence, preserving distinct duplicate slots. Forgotten bits on unused rows and reserved high bits remain represented. Current-profile conditions remain authoritative. Older components without these IDs keep their legacy current-map interpretation; they cannot establish a lost historical mapping after an unrelated kernel changed it. New captures carry the mapping explicitly.

An observed opaque baseline with no reconciled current profile remains unsupported for component capture. Current progression is authoritative; unique known non-item recovery abilities retain the existing dormant merge policy. When item-taught recovery exists, optional `PendingGuardianForceRecovery` preserves all sixteen nullable historical rows separately, including colliding records, learned/AP/forgotten/item-taught/active facts and initialization state. Restore maps current progression through selected definitions first, then attaches pending history without granting or clearing an ability. Ordinary AP and compatibility normalization preserve that separate history. Absence means no pending history, so older components remain readable. Compiled recovery profiles/templates and prior profile-undo attribution are excluded. Original-format export reports pending recovery as an explicit loss requiring the existing conversion choice.

The optional `GuardianForceIntent` character member preserves save-local authoring documents, excluded contributions and local ownership aliases. Its version-1 DTO whitelists document/operation IDs, GF/ability IDs, replacement and initial-state choices, expected state/order and stable producer references. It supports the existing Ensure Ability, Replace Ability, Set Initial State and Order Subset contracts. Earned AP, learning selection, passive preference and form enable remain in their existing progression/preference owners; AP requirements come from the selected ability-point table rather than a saved installed template.

Capture verifies that the intent is already reconciled with current definitions; it does not turn a pending edit into committed progression. Restore composes the selected installed source/layers, saved exclusions and ordered local operations using the existing composer, then projects known progress by identity. Saved local ownership takes precedence if an installed document later appears with the same ID, excluding that installed contribution. A changed-mod operation conflict or missing producer remains an explicit reconciliation boundary instead of a silently skipped choice. These failures leave both input component and selected definitions unchanged.

Replacing a resource-native ability retains its complete source-slot group. The effective learning view changes the referenced ability ID while preserving slot order, requirement and exclusion bytes; dependencies still refer to the same table indices. Learning, forgetting, AP ownership, compatibility projections and semantic slot bindings use that view. Replacement into an already present ability remains an explicit operation conflict, and partial or overlapping native bindings fail validation. Removed earned progress remains dormant by ability identity; a replacement uses its configured initial state rather than inheriting the removed ability's earned AP. Duplicate slots retain their distinct AP bytes and suppression flags, with AP awards still owned by the first matching slot. Neither installed source tables nor old snapshot schemas are rewritten.

Native fingerprints, arbitrary document/operation extension data, compiled templates and source resource references are not stored. Producer/document keys are portable opaque identities: separators and suffixes such as `local/abilities.json` are allowed and do not cause filesystem access. Actual rooted/drive/file-URI references refuse capture rather than creating environment dependencies. Fresh runtime authoring documents contain only the whitelisted fields, with no extension metadata or old source fingerprint. Older components missing `GuardianForceIntent` preserve the previous selected-definition behavior.

The per-save GF-form enable choice belongs to gameplay preferences in the broader progression coverage. An active form's invocation, timer and presentation remain battle execution state and are not part of this nonbattle character component. Existing execution snapshots and original-save readers/writers are unchanged.

## Durable progression and scene reconstruction

Version 2's `Progression` has explicit required owner groups; each nullable member preserves unknown/absent state rather than initializing it from zero. Missing a required version 2 group fails. `GameplaySaveRootOwnership` classifies every `GameState` property, and its regression test requires a review when a root member is added.

| Group | Saved progression | Exclusions or separate reconstruction |
| --- | --- | --- |
| Story | Exact event cells with original widths, including represented field-local values; world-entry bytes, controls, disc, saved battle flags/knownness, saved fade and message-variable values. | Uncertain executed event reads require a semantic adapter. Physical fades and their active callbacks are not copied. Canonical root values are used rather than frozen VM mirrors. |
| Saved world | Both vehicle slots, Garden/Ragnarok parking, committed transport-return values, fuel, world-event flags/channels, terrain knownness, original angle words and bounded unresolved saved entry values. Field party poses and the world entity configuration are separate logical values. | Loader receipts, native provenance rules, source frame, scripted camera trajectory and allocation identities are excluded. A resume handler must reconcile the current world pose with saved parked vehicles, establish a normal-load source and reject unsupported transport state. |
| Collections | Appearance, cards/statistics/RNG, shop bytes, recipe/discovery bits, shot flags, PocketStation values/name, Chocobo reward/import ledger, known magic, Scan history and refined-card IDs. | Kernel ammo tables, initialization fingerprints and asset data are supplied by installed definitions. Active card matches remain unsupported. |
| Rules and choices | Current/configured/pending preferences, magic-mode review, already-earned pending name requests and drafts, input settings, encounter policy/progress, playthrough policy and dialogue choice draft. | A pending choice is preserved as data; no claim is made that its suspended modal VM can yet be reconstructed. Pending encounters are rejected. |
| Clocks | Quest timer alternatives and their correlation, elapsed playtime/fraction, RNG state, draw depletion/regeneration, salary/rank/movement progress. | Installed salary tables are excluded. Small timer callback counts/display correlation currently remain because transaction/timer invariants use them; they are not a native allocation graph. |
| Transactions | Battle totals/persistent AI variables, applied result IDs, achievement outboxes/owner bindings, draw/mutation/dedup cursors and committed abandonment facts. | Former abandoned VM waits and next-operation pointers are excluded. The new coordinator must restore acknowledgement/transaction ownership before issuing new facts; it must not replay committed rewards. |
| Scene facts | Names, tutorials, raw field-party order, party/menu/run/map flags, place, previous salary movement and scoped logical music choices. | Extraction uses the active field snapshot or current world event context. World-only snapshots may take unchanged names/tutorials/party from the authentic suspended field; its music facts remain separately marked `SuspendedFieldMusic` and cannot claim current-world authority. No complete VM JSON is stored and frozen mirrors never replace current shared root globals. |
| Original compatibility residue | The bounded 8,192-byte original save image and its original names, when present, preserve fields that lack typed owners. | This image is historical compatibility residue, not the current game's authoritative whole-save projection. Current typed components and current scene names take precedence during reconstruction. It must not be treated as a current original save and reimported wholesale. |

The ordinary gameplay normal-load policy deliberately starts a fresh process and rebuilds native working storage. That includes stale physical battle headers, last-action/healing ranges and released staging residue, which can affect exact native process continuation. Accumulated battle totals, progression, pending facts and reward receipts are preserved separately. This is a declared normal-load semantic boundary, not a claim that the old physical rows never matter. Legacy exact-snapshot readers must continue to preserve those rows and their original continuation.

The host loader creates a fresh cold process, loads selected definitions, overlays durable progress and then constructs the supported scene. Local event values alone do not reconstruct actors, scheduler state or event stage. Resolved selected GF profiles and whitelisted local choices use the adapters above; ambiguous recovery and changed-operation conflicts fail explicitly rather than embedding old tables or silently losing progress. Existing snapshots retain their original continuation and reading behavior.

`GameplaySaveWorldData.RestoreParkingAndFlags` is a resource-free restoration primitive for parked vehicles and saved flags; it clears old return receipts instead of promoting a historical return to the current world pose. The current `Resume.World` position drives supported normal-load entry, while parked vehicles and occupancy remain consistent. Normal saved-world entry uses entry 62 rather than replaying a prior field-exit `WorldArrival`. Normal saved-field entry uses load reason 0, sharing the saved-load process initialization contract rather than field-request reason 1. The host establishes the initialized owners before applying these primitives.

A central host boundary evaluator and a validated semantic resume handler protect publication. Player control by itself does not prove that a field VM can be discarded. Live field continuation reconstructs retained logical actors and the scheduler without rerunning INIT or rewarding completed work again. Original-save imports instead use their normal-load entry intent. Unsupported active operations reject the new capture before replacing a slot; their existing execution snapshots remain readable.

## Logical field continuation

Field scripts can retain gameplay facts in locals and consumed operands. The continuation stores typed fibers, waits, operand frames and locals against the selected program identity. Physical field registration, model bytes, resource pointers, draw packets and historical opcode receipts are rebuilt. Current character equipment and explicit script appearance select current models; an old model buffer cannot override equipped weapons. Changing engine internals does not change this component contract. Replacing the field script itself still requires compatible script identity or an explicit semantic conversion; an arbitrary program-counter remap would risk duplicate rewards.

Optional owners cover background shade/scroll, actor camera selection, particle controls and supported Normal/Save script menus. Menu restoration reopens the actual panel with committed canonical changes, then uses the ordinary close/reentry transaction. It does not synthesize Cancel or Confirm. Particle geometry and draw pools come from current resources and start fresh. Actor camera target selectors derive from current retained actors; active interpolation uses current projection and completed endpoints remain held.

Ambient loop sound state retains only effect identity, voice and terminal volume/pan. Current installed descriptors supply sample data and loop policy. Loading restarts supported current loops from their beginning at those controls; one-shots, device buffers, playback offsets and ramp phase are excluded. The optional `LoopSounds` owner defaults to no retained ambient output when absent, matching earlier load behavior. Audio output restart does not step scripts, advance timers, allocate a native voice or replay old sound command receipts.

A resource-free historical execution-snapshot parse may still need selected initial Limit definitions. Such an in-memory state cannot be published as a current exact save or projected as durable gameplay progression until the original is loaded through the resource-aware reader. This preparation status is transient and introduces no new saved fields. Explicit represented values in current-schema saves keep their existing meaning.

When historical execution saves genuinely omit Limit features, the selected current initial definitions provide only those missing values. A changed template fingerprint does not replace represented progress or the saved owners' coherent initialization identity. A contradictory saved alias cannot supply missing values; complete historical owners retain their existing read contract.

Optional field PartyMovement retains consumed JOIN/SPLIT destinations, speeds and their held caller. Actor poses remain the sole current-position owner, and native stop distances derive from the operation. Saved BYTE194–196 bindings have a canonical owner distinct from runtime follow slots and generic event memory. Optional Scene.SavedPartyBindings records them only when the saved and runtime bindings differ; absence keeps the older mapping rule. Active waits require their complete owner. Displaced or backed-up MOVE remains an explicit unsupported capture boundary until its ownership is represented. No renderer phase or native operation receipt is added.
